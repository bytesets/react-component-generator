# commit

현재 작업 트리의 변경사항을 읽고, 의미 단위로 나누어, 일관된 한국어 컨벤션 메시지로 커밋한다. 사용자가 커밋을 요청한 시점에 이미 실행을 승인한 것으로 보므로, 별도의 확인 질문 없이 바로 커밋한다. 대신 무엇을 어떻게 커밋했는지는 끝에 투명하게 보고한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 무엇이 바뀌었는지 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 톤 참고
```

- git 저장소가 아니면(`git status`가 실패) 커밋할 수 없음을 알리고 중단한다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- untracked 파일은 diff에 나오지 않으므로 `git status`로 확인하고, 필요하면 내용을 직접 읽는다.
- diff가 매우 크면 파일별로 `git diff -- <path>`로 나누어 읽는다. 내용을 이해하지 못한 채 메시지를 쓰지 않는다.

### 2. 논리적 단위로 분류

한 커밋은 하나의 목적만 담아야 나중에 `git log`, `revert`, `bisect`가 쓸모 있다. 변경 파일을 아래 기준으로 묶는다.

- 새 기능 / 버그 수정 / 리팩터링 / 설정·문서·빌드 변경은 서로 다른 커밋으로 분리한다.
- 같은 기능에 속한 컴포넌트·스타일·테스트는 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`로 hunk 단위 분리를 제안한다(대화형 플래그는 쓸 수 없으므로, 불가능하면 한 커밋으로 묶되 사용자에게 알린다).
- 변경이 사실상 하나의 목적이면 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

(선택) 변경 이유와 맥락을 설명하는 본문
```

| type | 사용 시점 |
|------|-----------|
| feat | 사용자에게 보이는 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드·설정·의존성·문서 등 기타 |

규칙:
- 요약은 한 줄, 가급적 50자 안팎, 마침표 없이 쓴다. "~추가", "~수정", "~개선"처럼 명사형/간결한 어미로 끝낸다.
- "무엇을"보다 "왜/무슨 효과"가 드러나게 쓴다. diff를 읽으면 알 수 있는 파일명 나열은 피한다.
- 본문은 요약만으로 부족할 때만 쓴다.
- 비밀값(.env, 키, 토큰)이 변경에 포함돼 있으면 커밋 대상에서 빼자고 경고한다.

예시:
- `feat: 컴포넌트 생성 폼에 props 타입 선택 기능 추가`
- `fix: 빈 이름 입력 시 생성 버튼이 활성화되는 문제 수정`
- `refactor: 템플릿 렌더링 로직을 별도 유틸로 분리`
- `chore: eslint 설정 업데이트`

### 4. 바로 커밋하고 결과 보고

확인 질문 없이 커밋 단위마다 해당 파일만 명시적으로 stage하고 커밋한다.

```bash
git add <파일들>
git commit -m "<type>: <요약>"
```

- `git add -A`/`git add .`는 계획에 없는 파일(비밀값, 빌드 산출물)이 섞일 수 있으므로 쓰지 않는다.
- 비밀값(.env, 키, 토큰)처럼 커밋하면 안 되는 파일은 승인 절차가 없는 만큼 더 엄격하게 제외하고, 제외했다는 사실을 보고에 적는다.
- pre-commit hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 알리고 고친 뒤 새 커밋으로 진행한다.
- 모두 끝나면 `git log --oneline -N`으로 만든 커밋 목록과 포함된 파일을 보여준다. 잘못 커밋했을 때 사용자가 바로 알아채고 `git reset`/`amend`로 되돌릴 수 있게 하기 위해서다.
- push는 사용자가 요청할 때만 한다. 원격에 올라가면 되돌리기 어렵기 때문이다.
