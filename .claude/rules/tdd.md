# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 쓰는 **기본값(fallback)** 이다.
- 충돌하는 항목만 프로젝트 규칙을 따르고, 나머지는 이 파일을 따른다.

## 1. 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리, 에러 매핑)
- **유틸 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (로직 없이 마크업·스타일만 있는 컴포넌트)
- SQL

경계가 애매하면 **적용하는 쪽**으로 판단한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 테스트 하나에 여러 동작을 섞지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. import 오류, 오타, 문법 오류, 설정 문제로 실패했다면 테스트부터 고쳐서 올바른 이유로 실패하게 만든다.

### GREEN: 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 옵션, 분기, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 리팩터링 후 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. 그 프로덕션 코드를 **삭제**한다.
2. **RED부터 다시 시작**한다.

- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 남겨둔 코드는 테스트를 코드에 끼워 맞추게 만든다. 테스트가 먼저 설계를 이끌어야 한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 몇 줄이면 끝나고, 나중에 단순하지 않게 변할 때 회귀를 막아준다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 이미 만든 코드를 그대로 확인할 뿐이라 결함을 못 잡는다. 실제로 "나중"은 오지 않는다. |
| "시간이 없다" | 디버깅과 재작업이 TDD보다 오래 걸린다. 급할수록 실패하는 지점을 먼저 고정해야 한다. |
| "삭제하면 낭비다" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이며, 테스트 주도로 다시 쓰면 보통 더 빨리 끝난다. |
| "프로토타입이다" | 프로토타입은 곧 제품이 된다. 버릴 코드라면 테스트도 얇게 쓰면 되지만, 로직이 있으면 RED부터 시작한다. |

## 체크리스트

- [ ] 테스트를 **먼저** 작성했다
- [ ] 실행해서 **"기능 미구현"** 으로 실패하는 것을 봤다
- [ ] 통과시키는 **최소 코드**만 작성했다
- [ ] 신규 + 기존 테스트가 **모두 green**이다
- [ ] 리팩터링 후에도 **green**이고 새 동작은 없다
